# Crumb 0.0.1-rc.8 candidate

This prerelease changes how the iOS SDK is packaged, and nothing else. Native
iOS no longer includes PLCrashReporter, and the CocoaPods pods are built so that
CocoaPods trunk accepts them. The report format, the JavaScript API and the
Android SDK are the same as in rc.7. The [CHANGELOG](../../CHANGELOG.md) lists
each change.

rc.8 is intended to be the last candidate before stable 0.0.1, and the first
Crumb version on CocoaPods trunk since rc.3.

Source preparation does not establish registry availability or complete pilot
acceptance. Stable 0.0.1 remains a separate release.

## Exact distributions

| Distribution | Candidate identity |
| --- | --- |
| Native iOS, Swift Package Manager | Tag `0.0.1-rc.8`, products CrumbCore and CrumbUI |
| Native iOS, CocoaPods | `CrumbSDK`, `CrumbSDKCore` and `CrumbSDKUI` at `0.0.1-rc.8` |
| Android, Maven Central | `com.crumbsdk:crumb-core:0.0.1-rc.8`, `com.crumbsdk:crumb-ui:0.0.1-rc.8` and `com.crumbsdk:crumb-react-native:0.0.1-rc.8` |
| React Native / Expo | `@crumbsdk/react-native@0.0.1-rc.8`, npm channel `next` |
| Standalone source-map CLI | `@crumbsdk/source-maps@0.0.1-rc.8`, npm channel `next` |

Native tag `0.0.1-rc.8` and adapter tag `react-native-v0.0.1-rc.8` must identify
the same independently reviewed merge commit. VERSION synchronizes the native SDK
constants, both npm package versions, the adapter native pin and the CLI lockfile.
Existing tags and registry versions must never be replaced.

All three Maven artifacts publish together, because the adapter resolves
`com.crumbsdk:crumb-react-native` at its own version. The Android sources are
unchanged since rc.7 apart from the version constant.

The adapter keeps its exact, compatible `@crumbsdk/source-maps@0.0.1-rc.4`
uploader dependency, as rc.7 did. The CLI has no source changes since rc.6; the
standalone package is versioned rc.8 with the other distributions.

## What changes

### Native iOS no longer includes PLCrashReporter

From rc.4 to rc.7 the Swift package and the `CrumbSDKCore` pod depended on
PLCrashReporter 1.12.0. Its only use was the native thread stacks recorded with
an opted-in React Native JavaScript failure, which a native application never
reaches. That capture now lives in the React Native adapter.

- **Swift Package Manager.** The Crumb package has no dependencies. If your
  project resolved PLCrashReporter only because of Crumb, it is dropped the next
  time packages are resolved.
- **CocoaPods.** `CrumbSDKCore` declares no dependency. A native app building
  with Xcode 27 needs no wrapper podspec or extra Podfile line; rc.7 documented
  one for the upstream pod's iOS 12.0 minimum.
- **Your own PLCrashReporter.** A native app that uses PLCrashReporter itself is
  no longer tied to the version Crumb pinned.

`Crumb.setJavaScriptCrashStackProvider` is a new public function that the
adapter uses to hand those stacks to the core. Applications do not call it.
Native Swift code that calls `Crumb.recordJavaScriptCrash` without the adapter
now records thread stacks as unavailable.

### CocoaPods

The pods are published for this candidate. `CrumbSDKCore` and `CrumbSDKUI` are
now always built as static frameworks, including in an app whose Podfile uses
`use_frameworks!`. rc.7 was rejected by trunk's validation because the dynamic
build placed a statically linked binary beneath a dynamic framework; that
dependency is gone as well.

The release checks now validate each pod the way trunk does, as a dynamic
framework build with no third-party podspec supplied, and the umbrella pod as a
static build too.

`pod "CrumbSDK", "0.0.1-rc.8"` resolves only once the registry job has finished
and its verification has passed. CocoaPods trunk becomes read-only on 2 December
2026. Pods published before then stay installable, and new native iOS
integrations should still prefer Swift Package Manager.

### React Native and Expo

There is no JavaScript API or configuration change. Installation is the same:
the Podfile helper or the Expo config plugin installs the native pods and
PLCrashReporter from files bundled in the npm package.

The adapter pod now declares PLCrashReporter itself and is a static framework.
Native thread stacks are still recorded with a JavaScript failure only when
JavaScript crash capture is enabled and `thread_stacks` evidence is allowed, and
the core applies the same limits and redaction to every frame as before.

Run `pod install` again and rebuild the native app after upgrading; regenerate
Expo native projects when using prebuild. An app that builds its pods as dynamic
frameworks has not been verified with this candidate or earlier ones.

### Upgrading

After publication, upgrade with your app's package manager:

```sh
npm install @crumbsdk/react-native@0.0.1-rc.8 react-native-nitro-modules@0.37.1
npx --no-install crumb doctor
```

Native Swift consumers use SPM with the exact `0.0.1-rc.8` tag, or
`pod "CrumbSDK", "0.0.1-rc.8"`. Native Android consumers use
`com.crumbsdk:crumb-ui:0.0.1-rc.8`.

Existing rc.7 users need no code or configuration change. Users upgrading from
rc.6 or earlier must read the [rc.7 release and migration notes](0.0.1-rc.7.md)
first: reports queued before rc.7 are not uploaded automatically, and an app
must not roll back to rc.6 once a later version has queued a report.

Support floors are unchanged: React Native 0.79+, iOS 15.1+ for the adapter,
Android API 26+, Nitro 0.37.1, and Node.js 22+ for build commands. Native iOS
requires iOS 15+, and native Android requires API 26+ and Java 17 bytecode.
Expo requires a development or production build; Expo Go is unsupported.

## Publication after independent review

1. Merge the preparation PR after independent review and passing checks. Record
   the exact merge commit and verify version and tag checks on that commit.
2. Create the immutable tags `0.0.1-rc.8` and `react-native-v0.0.1-rc.8` on that
   same commit. Wait for **Native SDK release** and verify its manifest revision,
   archives and `SHA256SUMS`. Confirm the Maven archive contains all three
   coordinates.
3. Run **Publish native registries** with tag `0.0.1-rc.8`, registry `both`, and
   confirmation `publish 0.0.1-rc.8`. The CocoaPods and Maven jobs run
   independently, so one failing does not stop the other. Record the Xcode
   version the CocoaPods job prints.
   - CocoaPods validates each pod before uploading it and publishes Core, UI and
     the umbrella pod in that order. If a pod fails validation, that pod and the
     ones after it are not uploaded.
   - If the job stops part-way, rerun the workflow with registry `cocoapods`. It
     skips every pod that trunk already holds at this version.
   - A defect in a podspec cannot be corrected at this version. It moves to the
     next version, and SPM, Maven and npm for rc.8 are unaffected.
4. **Before any npm publication,** confirm
   `com.crumbsdk:crumb-react-native:0.0.1-rc.8` resolves from Maven Central:
   `npm run registry:verify -- --maven`. The React Native publish workflow checks
   versions and tags but not Maven availability, so this ordering is the only
   guard against publishing an adapter that cannot build.
5. Run **Publish source-map CLI to npm** with tag `0.0.1-rc.8`, channel `next`,
   and confirmation `publish @crumbsdk/source-maps@0.0.1-rc.8`.
6. Run **Publish React Native SDK to npm** with tag `react-native-v0.0.1-rc.8`,
   channel `next`, and confirmation `publish @crumbsdk/react-native@0.0.1-rc.8`.
7. Verify exact versions, integrity, channel, bundled dependency resources and
   native pins. Confirm a fresh adapter installation exposes `crumb setup` and
   includes its pinned uploader. Do not promote npm `latest`.
8. Build fresh SPM, CocoaPods, Maven, bare React Native and Expo consumers from
   the final published artifacts before updating installation availability
   claims. Then update the public quickstarts to rc.8 for the distributions it
   reached.

Only the release coordinator performs these separately authorized manual actions
with existing workflows and credentials. Preparation checks do not publish.

## Validation and remaining acceptance

Version and contract checks, native release checks and artifact verification,
npm quality and packaging checks and path-triggered examples must pass on the
reviewed candidate commit. A toolchain-specific local failure must be disclosed
rather than bypassed or reported as a pass.

Two things are specific to this candidate and are not established by the
preparation checks:

- **The moved capture, on a device.** The preparation ran a Release build of the
  adapter example on an iOS 26.4 simulator with a synthetic key and no upload
  destination, triggered a fatal JavaScript error and relaunched. The recovered
  report carried native thread stacks captured through the adapter. That is not
  a physical device and not a delivered report. On an iOS device, enable
  JavaScript crash capture with `thread_stacks` evidence allowed, trigger a
  fatal JavaScript error, relaunch, and confirm the delivered report carries
  native thread stacks.
- **CocoaPods from trunk.** Build a native app from the published pods on a
  current Xcode, once with `use_frameworks!` and once without.

The acceptance listed in the [rc.7 notes](0.0.1-rc.7.md#validation-and-remaining-acceptance)
still applies: the oldest supported React Native version, native Release builds
and real EAS Builds; fatal JavaScript crash, relaunch, exactly-once delivery and
decoding to the original file, function and line on both platforms; and privacy,
offline retry and customization coverage.

Keep reports, source maps, retained bundles, credentials and raw device evidence
private. Candidate publication does not imply these checks have passed.
