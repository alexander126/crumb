# Crumb 0.0.1-rc.7 candidate

This prerelease collects 45 changes merged since rc.6. They include privacy fixes
that change what reaches a durable report, queue and delivery reliability fixes,
a React Native Android release-build fix, Kotlin 2.0 compatibility for the Maven
artifacts, and a new Maven artifact that the React Native adapter requires. It is
also the first candidate since rc.3 to be published to CocoaPods trunk. The
[CHANGELOG](../../CHANGELOG.md) lists every change.

Source preparation does not establish registry availability or complete pilot
acceptance. Stable 0.0.1 remains a separate release.

## Exact distributions

| Distribution | Candidate identity |
| --- | --- |
| Native iOS, Swift Package Manager | Tag `0.0.1-rc.7`, products CrumbCore and CrumbUI |
| Native iOS, CocoaPods | `CrumbSDKCore`, `CrumbSDKUI` and `CrumbSDK` `0.0.1-rc.7` |
| Android, Maven Central | `com.crumbsdk:crumb-core:0.0.1-rc.7`, `com.crumbsdk:crumb-ui:0.0.1-rc.7` and `com.crumbsdk:crumb-react-native:0.0.1-rc.7` |
| React Native / Expo | `@crumbsdk/react-native@0.0.1-rc.7`, npm channel `next` |
| Standalone source-map CLI | `@crumbsdk/source-maps@0.0.1-rc.7`, npm channel `next` |

Native tag `0.0.1-rc.7` and adapter tag `react-native-v0.0.1-rc.7` must identify
the same independently reviewed merge commit. VERSION synchronizes the native SDK
constants, both npm package versions, the adapter native pin and the CLI lockfile.
Existing tags and registry versions must never be replaced.

**All three Maven artifacts publish together.** `crumb-react-native` is new in
this candidate and has never been published. The adapter resolves
`com.crumbsdk:crumb-react-native` at its own version, so a published adapter
cannot build on Android until that coordinate is on Maven Central. The
repository's own example resolves the native projects directly, so no local
build reveals a missing coordinate. Native Android integrations do not need
`crumb-react-native`.

The adapter keeps its exact, compatible `@crumbsdk/source-maps@0.0.1-rc.4`
uploader dependency, as rc.6 did. The CLI has no source changes since rc.6; the
standalone package is versioned rc.7 with the other distributions. Users do not
install a second Crumb package or align its version manually.

## Corrections and migration

### What changes in a report

Reports now redact more before they are stored. Credential-bearing values in
logs, diagnostic text, failure text and custom context are redacted on both
platforms, including quoted and escaped JSON values and partial authorization
and cookie values. The written description passes through the same redaction
before it is saved. Where a sensitive value's boundary cannot be established,
the rest of that input is redacted rather than risk a leak, so some diagnostic
context after it is deliberately lost.

On Android, a sensitive view that is scaled or rotated is now masked across its
real on-screen area, and a screenshot whose geometry cannot be resolved is
masked entirely. On iOS, removing a screenshot from the review screen now
removes it from the report.

Each report now records which project it was created for and is delivered only
to that project. Previously, an older queued report could go to a new project
after the project key or ingestion destination changed.

### Queued reports, upgrade and rollback

**Reports still waiting in the queue when an app upgrades to rc.7 are not
uploaded automatically.** They were written without an ownership record, so rc.7
cannot establish which project they belong to, and it will not guess. They stay
on the device, readable and durable, and still count toward the queue's limits
of 50 reports and 128 MiB. No operation removes them yet. Reports created after
the upgrade are unaffected.

Delivery is normally prompt, so most devices hold no pending reports when they
upgrade. A device that has been offline, or that holds uploads which failed
terminally, carries those reports forward and loses that much queue capacity. A
device holding 50 could not save a new report.

**Do not roll an app back from rc.7 to rc.6 or earlier once rc.7 has queued a
report.** rc.6 accepts only the earlier metadata version and treats an rc.7
record as a corrupt queue, which can block its queue operations until rc.7 or
later is restored. No downgrade migration is performed.

### Behavior you will notice

- The reporter closes once a report is saved, without a "Report saved" popup.
- Report sheets follow a downward drag and close on a tap outside them. A draft
  with content still asks before it is discarded.
- On iOS 26 and later, the report sheet, shake prompt and popup controls use
  native Liquid Glass. Earlier iOS versions keep their existing look, and Reduce
  Transparency selects the existing look on any version.
- On iOS, Crumb's requests no longer use the host app's shared cookie,
  credential or cache storage. Android cannot make the same guarantee, because
  `HttpURLConnection` consults the process-wide `CookieHandler`; `PRIVACY.md`
  describes the boundary.

### Android integrations

Start Crumb in the application's main process. In a process declared with
`android:process`, `CrumbReporter.install` now returns `false` and
`CrumbReportQueue.from` throws `CrumbReportQueueException.UnsupportedProcess`,
rather than letting two processes share one queue and drift its accounting.

`Crumb.recordJavaScriptCrash`, `Crumb.recoverJavaScriptCrashes` and
`CrumbReporter.recoverJavaScriptCrashes` were removed. React Native apps need no
change. Native Android code that called them directly should add
`com.crumbsdk:crumb-react-native:0.0.1-rc.7` and use
`dev.crumb.reactnative.CrumbJavaScriptCrashes`.

The Maven artifacts now publish Kotlin 2.0 metadata and depend on the 2.0.21
standard library, so Kotlin 2.0 projects can consume them. rc.6's artifacts
required Kotlin 2.2.

React Native Android release builds minified with R8 can construct the SDK
again; R8 previously removed the adapter's concrete Nitro class.

### CocoaPods

This candidate's pods depend on PLCrashReporter. Its upstream pod declares an
iOS minimum of 12.0, which Xcode 27 rejects; Xcode 26.6 still accepts it.
CocoaPods applies a pod's own declared minimum even when your Podfile asks for a
higher platform, so on Xcode 27 select Crumb's wrapper, which uses the same
pinned PLCrashReporter binary at iOS 15.0:

```ruby
platform :ios, "15.0"

target "YourApp" do
  pod "PLCrashReporter", :podspec =>
    "https://raw.githubusercontent.com/alexander126/crumb/0.0.1-rc.7/distribution/cocoapods/PLCrashReporter.podspec"

  pod "CrumbSDK", "0.0.1-rc.7"
end
```

The wrapper keeps the pod name `PLCrashReporter`, so it replaces the upstream pod
rather than linking a second copy. Upgrading from the rc.3 pods, which had no
PLCrashReporter dependency, adds one. Swift Package Manager remains the
recommended path for new native integrations and needs no equivalent line.
CocoaPods trunk becomes read-only on 2 December 2026, so this may be the last
Crumb version published there.

### Upgrading

After publication, upgrade with your app's package manager:

```sh
npm install @crumbsdk/react-native@0.0.1-rc.7 react-native-nitro-modules@0.37.1
npx --no-install crumb doctor
```

Rebuild the native app after upgrading and regenerate Expo native projects when
using prebuild. Preserve your current configuration and the bundled Podfile
helper or Expo plugin. Existing rc.6 users need no JavaScript API migration.
Earlier users should also follow the [rc.5 migration](0.0.1-rc.5.md) and the
[rc.4 bundled-native migration](0.0.1-rc.4.md).

Native Swift consumers use SPM with the exact `0.0.1-rc.7` tag, or the CocoaPods
installation above. Native Android consumers use
`com.crumbsdk:crumb-ui:0.0.1-rc.7`.

Support floors are unchanged: React Native 0.79+, iOS 15.1+ for the adapter,
Android API 26+, Nitro 0.37.1, and Node.js 22+ for build commands. Native iOS
requires iOS 15+, and native Android requires API 26+ and Java 17 bytecode.
Expo requires a development or production build; Expo Go is unsupported.

## Publication after independent review

1. Merge the preparation PR after independent review and passing checks. Record
   the exact merge commit and verify version and tag checks on that commit.
2. Create the immutable tags `0.0.1-rc.7` and `react-native-v0.0.1-rc.7` on that
   same commit. Wait for **Native SDK release** and verify its manifest revision,
   archives and `SHA256SUMS`. Confirm the Maven archive contains all three
   coordinates.
3. Run **Publish native registries** with tag `0.0.1-rc.7`, registry `both`, and
   confirmation `publish 0.0.1-rc.7`. Its CocoaPods job selects Xcode 26.6,
   because `pod trunk push` validates against upstream PLCrashReporter and cannot
   use the wrapper. Wait for propagation and the clean consumer checks. This step
   must finish before CocoaPods trunk becomes read-only on 2 December 2026.
4. **Before any npm publication,** confirm
   `com.crumbsdk:crumb-react-native:0.0.1-rc.7` resolves from Maven Central:
   `npm run registry:verify -- --maven`. The React Native publish workflow checks
   versions and tags but not Maven availability, so this ordering is the only
   guard against publishing an adapter that cannot build.
5. Run **Publish source-map CLI to npm** with tag `0.0.1-rc.7`, channel `next`,
   and confirmation `publish @crumbsdk/source-maps@0.0.1-rc.7`.
6. Run **Publish React Native SDK to npm** with tag `react-native-v0.0.1-rc.7`,
   channel `next`, and confirmation `publish @crumbsdk/react-native@0.0.1-rc.7`.
7. Verify exact versions, integrity, channel, bundled dependency resources and
   native pins. Confirm a fresh adapter installation exposes `crumb setup` and
   includes its pinned uploader. Do not promote npm `latest`.
8. Build fresh SPM, Maven, bare React Native and Expo consumers, and CocoaPods
   consumers on both Xcode 26.6 and Xcode 27, from the final published artifacts
   before updating installation availability claims. Then update the public
   quickstarts to rc.7, including a CocoaPods tab that carries the wrapper line.

Only the release coordinator performs these separately authorized manual actions
with existing workflows and credentials. Preparation checks do not publish.

## Validation and remaining acceptance

Version and contract checks, native release checks and artifact verification,
npm quality and packaging checks and path-triggered examples must pass on the
reviewed candidate commit. A toolchain-specific local failure must be disclosed
rather than bypassed or reported as a pass.

Published-consumer, physical-device and hosted acceptance remain separate. In
particular, test the oldest supported React Native version, native Release
builds and real EAS Builds; exercise fatal JavaScript crash, relaunch,
exactly-once delivery and decoding to the original file, function and line on
both platforms. Verify raw stacks remain explicit when maps are absent or wrong.
An upload receipt alone is not proof of decoding. Export dry runs do not prove
on-device updates or rollback. Complete privacy, offline retry and customization
coverage and resolve critical and high-severity defects before pilot acceptance.

Keep reports, source maps, retained bundles, credentials and raw device evidence
private. Candidate publication does not imply these checks have passed.
