# Crumb 0.0.1-rc.5 candidate

This prerelease packages guided React Native/Expo setup and automatic release
source maps. Source preparation does not establish registry availability or
complete pilot acceptance. Stable 0.0.1 and production promotion remain separate.

## Exact distributions

| Distribution | Candidate identity |
| --- | --- |
| Native iOS, Swift Package Manager | Tag `0.0.1-rc.5`, products CrumbCore and CrumbUI |
| Android, Maven Central | `com.crumbsdk:crumb-core:0.0.1-rc.5` and `com.crumbsdk:crumb-ui:0.0.1-rc.5` |
| React Native / Expo | `@crumbsdk/react-native@0.0.1-rc.5`, npm channel `next` |
| Standalone source-map CLI | `@crumbsdk/source-maps@0.0.1-rc.5`, npm channel `next` |

Native tag `0.0.1-rc.5` and adapter tag `react-native-v0.0.1-rc.5` must identify
the same independently reviewed merge commit. VERSION synchronizes native SDK
constants, both npm package versions, the adapter native pin and CLI lockfile.
Never replace an existing tag or registry version.

The React Native package deliberately depends on the already-published exact
`@crumbsdk/source-maps@0.0.1-rc.4`: its uploader API is compatible and unchanged.
It is installed automatically and stays out of the app's runtime bundle. The
standalone CLI rc.5 includes corrected npm 12 packaging checks. Consumers do
not need to install or align a second Crumb package manually.

## React Native / Expo installation and migration

After rc.5 publication, use your app's package manager to install:

```sh
npm install @crumbsdk/react-native@0.0.1-rc.5 react-native-nitro-modules@0.37.1
npx --no-install crumb setup
npx --no-install crumb doctor
```

Setup previews edits before applying them. Choose source maps when JavaScript
crash reporting is wanted, and use the project's upload origin and dedicated
build-only credential. Keep the normal SDK startup configuration and explicitly
enable JavaScript crash capture. Ordinary user reports work without source maps.

Remove a manually configured `release.bundleVersion` when adopting automatic
build hooks: the exact JavaScript bundle now supplies its own identity. Preserve
your existing initialization and other configuration. Custom pipelines can retain
the explicit manual release tuple by not enabling the automatic hooks.

Native app versions/builds are captured when failures occur, so relaunching an
upgraded binary does not re-label an older failure. Uploads use final build output
and composed Hermes maps. Failed uploads warn by default, retain exact artifacts
for retry, and can fail CI with strict mode. See the
[guided setup guide](../react-native-setup.md) for secrets, supported configuration
shapes, retained receipts, and explicit Expo export targets.

Rebuild the native app after upgrading. Expo requires a development or production
build, never Expo Go. For rc.3 migrations, keep the bundled native Podfile helper
or Expo plugin described in the [rc.4 migration](0.0.1-rc.4.md); remove old manual
Crumb pod declarations before adopting the helper. Preserve higher app targets:
React Native 0.79+, iOS 15.1+, Android API 26+, Nitro 0.37.1, and Node.js 22+ for
build commands. Dynamic or ambiguous project configuration receives manual setup
instructions rather than automatic edits.

Native Swift apps use SPM with the exact rc.5 tag and both products; native Android
apps use the exact Maven coordinates above. Their integration APIs are unchanged.
CocoaPods trunk publication is not required; rc.3 pods remain the legacy path.

## Publication after independent review

1. Merge the green preparation PR through an independent authorized reviewer.
   Record its exact commit and verify version/tag checks on that commit.
2. Create both immutable tags on that commit. Wait for **Native SDK release**;
   verify the release manifest revision, archives and SHA256SUMS.
3. Run **Publish native registries**, tag `0.0.1-rc.5`, target `maven`, confirmation
   `publish 0.0.1-rc.5`. Wait for propagation and the clean Maven consumer check.
4. Run **Publish source-map CLI to npm**, tag `0.0.1-rc.5`, channel `next`,
   confirmation `publish @crumbsdk/source-maps@0.0.1-rc.5`.
5. Run **Publish React Native SDK to npm**, tag `react-native-v0.0.1-rc.5`, channel
   `next`, confirmation `publish @crumbsdk/react-native@0.0.1-rc.5`.
6. Verify exact registry versions, integrity, channel and native dependency pins.
   Confirm a fresh adapter install exposes `crumb setup` and includes its pinned
   uploader without a second manual install. Do not promote npm `latest`.
7. Run fresh SPM, Maven, bare RN and Expo consumers from published artifacts.
   Promote quickstarts and dashboard availability copy after the corresponding
   installation path passes; retain versioned migration instructions.

Use existing publication workflows and credentials. Missing registry access is a
concrete blocker, not a reason to bypass release checks or invent package names.

## Remaining acceptance checks

- Verify CI and package checks on the exact approved candidate commit.
- Test final published packages; source-linked builds and local archives alone
  do not establish registry-consumer compatibility.
- Build bare React Native Release consumers, including the oldest supported RN
  version, and real EAS Builds with final auto-incremented native build values.
- Exercise fatal JavaScript crash, relaunch, exactly-once delivery and hosted
  decoding to the known original file/function/line on iOS and Android.
- Verify missing/incorrect maps retain explicit raw stacks; an upload receipt
  alone is not proof of a decoded crash.
- Exercise exact Expo update exports, on-device updates and rollback. Export
  dry runs do not prove EAS publication or rollback behavior.
- Complete privacy, offline retry, customization, and available physical-device
  coverage before accepting the pilot; resolve critical/high-severity defects.

Keep reports, source maps, retained bundles, credentials and raw device evidence
private. Candidate publication does not imply these acceptance checks have passed.
